# Agent Note: 文档读数真实性门（在役面 / 全量快照分离 + 档自述读数）
Status: proposed

## Problem

优化计划 O8 的验收原文是「当前版本、人读索引和机器装载面一致；未实跑的全量明确待验」。
核实基线（v3.284.0）时的真实状态是：**人读文档里的读数不在任何判据的枚举面内**。

- README 同时写着 `` `extra_js`（79 项） `` 与 `` `extra_js` 78 项 ``（自相矛盾）；
- README 的「当前版本」停在 `3.271.0`，而磁盘已是 `3.284.0`；
- README「248 个测试文件」与 PLAN「246 测试文件」互相打架，两个都不是磁盘真值（264）；
- PLAN 现状基线停在 `v3.266.0` / `index.js 13883 行`。

这与 v3.279.0「判据的面漏一类，结论就完全反了」同族：版本四源有 `scan_version_guard` 把守，
运行时成功声称有 `scan_claim_truthfulness` 把守，但**文档里的数字只有人眼**。
漂移已经发生且无人发现，属于「门禁成本与当前事实不一致」的典型形态。

第一版扫描器（本刀中途被推翻的那版）把「登记版本 ≠ 当前版本」直接判红。后果很严重：
**「新增一个测试文件」与「文档说谎」变成同形** —— 想过门禁的唯一办法是提前跑全量，
而用户当下的执行纪律明确禁止（计划全部内容完成前不跑全量）。判据一旦与执行纪律冲突，
结果必然是判据被绕过或被长期豁免，那比没有判据更坏。

同一轮还发现第二类洞：文档里的**逐版自述**同样是读数。本刀自己在 CHANGELOG 里写
「`tests/v3285_...test.mjs`（13 条）」，而该档实际 15 条；历史节里另有三处同类自述与今日磁盘有差
（v3220 17/18、v3164 18/19、v3162 18/22）。前者是**漂移**，后者是**时点**，必须区分处置。

## Proposal

新增扫描器 `tests/audit/scan_doc_truthfulness.mjs`（D1~D9，退出码三档 0/1/2）
与 `tests/v3285_o7_doc_truthfulness.test.mjs`（16 条），并建立三条口径。

**口径一：把「当前在役面」与「最近一次全量实跑快照」拆成两条读数。**

- 在役面：README/PLAN 各一行，写**磁盘枚举**读数（测试文件数 / 审计门禁数 / 审计磁盘数）。
  盘上加了文件 ⇒ 这一行立刻变，门禁仍然绿。判据只核对「这一行 ↔ 磁盘」，不涉及实跑。
- 快照：写「最近一次全量实跑」的四元组（版本·测试·断言·审计），真源是
  `tests/audit/doc_readings.json`；未实跑时文档**必须**写「当前版本 vX **全量待验**」。
- **反向也判**：登记已对齐当前版本却仍留「待验」标记 ⇒ 翻红（把已实跑说成没跑，同属读数不实）。

**口径二：实跑读数零手抄，且扫描器绝不自己跑全量。**

断言数只能来自一次真跑：`TEST_SUMMARY_JSON=<path> node tests/run.mjs --audit` 的结构化摘要，
由 `tools/_rebind_doc_readings.py` 消费并写入 `doc_readings.json`（`rebinds` 追加留痕，不覆盖历史）。
扫描器只核对「文档 ↔ 登记」。审计段跑全量会**自指**（本扫描器自己就在审计面内），
且会把 33s 的审计拖到 90s+。这条以「实现里不得出现起子进程能力」的形式**被 D9 反向核对**。

**口径三：档自述读数按「当前版本节」判，历史节不判。**

- 条数：CHANGELOG 顶节（第一个 `## vX.Y.Z` 之前）里凡是「`tests/<file>.test.mjs`（N 条）」
  逐字给出全路径 + 紧邻条数的地方，核回磁盘（文件在场性 + `^test(` 条数）。
- 契约声明：该节若写「退出码三档」⇒ 实现里必须真有 `process.exit(0/1/2)` 三个出口；
  若写「绝不跑全量」⇒ 实现里不得出现任何起子进程的能力。
- 历史节的同类自述**不判**。理由：那是**当时**的真读数（此后被追加用例），
  判它等于要求每版回头改写历史节 —— 本仓早已把这种「抬版仪式」定性为反模式（T1）。

## Alternatives Rejected

1. **全量实跑作为过门条件**（首版）。与用户执行纪律直接冲突，且把「加文件」和「说谎」同形。
   被本刀自己推翻，改为「在役面 / 快照分离 + 待验标记正反向判定」。
2. **扫 CHANGELOG 全篇的档自述**。历史节三处立刻转红，而它们不是缺陷 ——
   那就必须再给历史节开豁免清单，豁免清单一长就退化成「判据在量一个不是缺陷的东西」。
   收窄到顶节后，判据面对的恰好是「抬版时真的会写错」的那一段。
3. **判 CHANGELOG 顶节的日期**（首版 D9 的日期支路）。实测 CHANGELOG 通篇不写日期 ⇒
   该判据**永不触发**，正是本仓自己定性过的「恒绿探测器」（v3226 C2）。已换成上面两条可触发的契约核对。
4. **让扫描器自己跑全量拿断言数**。自指 + 成本翻三倍，且会让「审计门禁」互相启动。
   坚持「跑一次 → 落盘 → 重绑」的单向流。
5. **把断言的数字写进扫描器常量**。那就是第二份真源，与 O8 要治的「两处各说各话」同病。

## Consequences

- 文档说谎与「盘上多了文件」从此**不同形**：前者红、后者只是读数变。抬版时不再被迫提前跑全量。
- 实跑读数只能经重绑工具写入；工具 fail-closed（八条）挡住「失败摘要 / 缺 audit / 旧版摘要」
  被照签成真读数 —— 否则扫描器会忠实地拿假数字去核对文档，两边一起绿。
- CHANGELOG 顶节的自述条数成为**受判读数**：改档的条数必须同步改顶节，否则红。
  这是本刀新加的一条维护义务，接受它，因为它恰好覆盖抬版时真会写错的那一段。
- 历史节三处时点差**保持原样**（按 T1 不回头改），如实写在 CHANGELOG 边界段，
  不写进判据 —— 写进去只会产出必须永久豁免的假红。
- D9 的实现必须读**正在运行的这个脚本自己**（`fileURLToPath(import.meta.url)`），
  不能读 `ROOT` 下的同名文件：夹具模式下 `ROOT` 是合成仓，那里没有本扫描器，
  首版按 ROOT 读导致健康夹具直接崩（实测 B1 由绿转红）。
