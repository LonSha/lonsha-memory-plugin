# 第二十四期 · LonSha 记忆插件优化九项（L24-O1~O9）

> **主题：从「什么都记得」到「记得准、取得快、看得见」。**
> 本仓 395→408 个模块、551 套判据、`manifest.extra_js` 408 项全部真加载 —— **零件已经太多**。
> R21~R23 三期做的都是「把已登记的账对齐」（拆行数、清零消费、补回执、三态覆盖）。
> 但有三件事从未被任何一期作为**产品能力**处理：
> ① 召回**准不准**没有任何可复现的度量；② 记忆**多了以后**会怎样没人测过；③ 引擎对用户**不可见**。
> 九项全部落在这三件事上。判据与台账是默认纪律，不占名额。

## 0. 立项前核对（2026-11-18 实读 `vector-semantic-sparse-hybrid-retrieval.js` 全文 102 行后）

> 纪律：**发现账实不符先记账，不许把「名字像」当「机制在」**。
> 通道限制如实记：本轮 `grep` / `code_runner` 不可用，「某模块有没有被消费」**无实测证据**，涉及消费的一律 `【待复核】`。

| 初稿假设 | 实读结果（逐行核对，非推测） | 改后口径 |
|---|---|---|
| 融合器要从零搭 | `fuseRRF()` 已实现标准 RRF：`1/(60+rank)`，`sparseWeight 0.45 / denseWeight 0.55`，且**逐条返回 `sparseRank` / `denseRank` / `hybridScore`** | `O1` 改为「**把骨架补成引擎**」，不是从零搭融合器；「没有任何一路报贡献」这句撤回（每条已有路秩），改指**整路统计缺席**（进来/并入/重复/跳过各几条） |
| 稀疏路是 BM25 | `calculateSparseScore()` 实体是 `lowerDoc.includes(term)` 命中词数 ÷ 查询词数 —— **无 IDF、无 tf 饱和、无长度归一**，函数注释自称「BM25 近似」 | 这是本仓最典型的「**叫 BM25 但不是 BM25**」。真缺口在此：补 IDF / tf 饱和 / 长度归一，并与现有比例分**对拍**（同一批 query 排名变化必须可解释） |
| 该模块已在生产路径上跑 | 文件尾 `[v3.461.0 接线修复]` 明写：此前是 ESM（`export`），而 `manifest.extra_js` / 审计沙箱 / `optional-engine-registry` 全按经典脚本加载 ⇒ `export` 是语法错误，**真机上从未挂载成功**，此版才改回 UMD/IIFE | 任何以「融合已在跑」为前提的条目降级为 `【待复核：消费点】`。`O1` 验收口径加一条：**接线后必须有一条「真装载 + 真召回」的端到端判据**，不许只测纯函数 |
| 延迟读数/索引一律为零 | 只能确认 `async-indexing-pipeline-debouncer.js` 从名字看是管线调度而非索引结构（**未读全文**） | `O2` 保留，但「仓库里没有任何召回延迟读数」这句标 `【待复核】`；开工第一步是补读数，不是先建索引 |

结论：`O1` 的核心缺口从「没有融合」变成「**融合在、但稀疏路名不副实，且模块曾长期不可装载**」——这比原判更值钱，也更危险（不报错、不崩溃、只是排得不对）。

## O1 · 召回内核：从字符 n-gram 到可解释的三路融合

**缺什么**：现在的「向量」是 `local-ngram-vectorizer.js` 的字符 n-gram 余弦 —— 中文短句够用，
但同义改述（「他答应过要回来」vs「他说会回来」）基本靠运气。`vector-semantic-sparse-hybrid-retrieval.js`
只有 4482 字节，是**骨架不是引擎**。更关键的是：融合之后**没有一路报贡献**，无法回答「这条为什么被召回」。

**做什么**：
1. 三路候选：**BM25（词）** + **字符 n-gram（现有一路保留）** + **可选向量路**（宿主提供 embedding 时启用，缺则 `absent` 不塌成 0）；
2. 融合用确定性 RRF，**逐路报贡献**（进来几条 / 并入几条 / 重复几条 / 跳过几条）；
3. 查询改写：同义/指代（「他」→ 最近活跃主语）只在有证据时做，证据不足 `unknown`；
4. 每条召回附**命中解释**：命中哪一路、命中哪个词/片段、来自哪条记忆的哪个字段。

**验收口径**：同一查询在同一记忆库上**两次结果完全一致**（确定性）；
关掉某一路后结果可解释地变化（不是随机漂移）；每条结果都有可读的命中理由（缺理由即不合格）。

## O2 · 召回性能：延迟预算与增量索引

**缺什么**：记忆是**线性扫描 + 现场打分**，记忆量一大就慢。仓库里**没有任何召回延迟读数**，
也没有索引（`async-indexing-pipeline-debouncer.js` 是管线调度，不是索引结构）。

**做什么**：
1. 建倒排索引（词 → 记忆 id）+ 会话内增量更新（新记忆入索引，不重建全库）；
2. 实测三档规模（1k / 1w / 10w 条记忆）的召回 P50 / P95 延迟与内存占用，落成可复跑脚本；
3. 降级链：索引不可用时退回线性扫描，**但读数面必须 `degraded` + 原因**（不许静默变慢）；
4. 增量索引与全量重建的召回结果对拍**逐条一致**（索引只改速度不改结果）。

**验收口径**：10w 条下 P95 有明显下降（给实测值）；索引与线性扫描结果逐条一致；
索引失效时降级可见且可自愈（重建后回到正常路径）。

## O3 · 加载期性能：装配分层与冷启动预算

**缺什么**：`index.js` 13546 行，`MemoryEngine` 8500 行 + 48 个 IIFE 依赖，**入口 L12685 在装载期就实例化**。
冷启动把整台引擎拉起来，而用户可能只是打开设置页。仓库**没有冷启动读数**。

**做什么**：
1. 装配分层：装载期只注册（描述符 + 懒 getter），**首次真正需要时才实例化**；
2. 冷启动预算读数：装载耗时、实例化耗时、首条记忆可用时间三项；
3. 惰性化不得改变可观察行为：装载后任何 API 的返回值与急加载**逐字段一致**；
4. 老宿主降级路径（无 `Proxy`）单独测一遍，读数分开报。

**验收口径**：装载耗时相对 v3.474 基线下降（给实测值）；惰性 vs 急加载的 API 返回值对拍零差异；
「只打开设置页」这一场景下引擎核心未被实例化（读数证明，不是字符串断言）。

## O4 · 记忆规模治理：分层、分片与落界

**缺什么**：`memory-capacity-watermark.js` 只报「水位」，`sleep-consolidation-graph-pruner.js` 只做图剪枝。
**没有分层存储**（热/温/冷）、**没有按会话分片**、**没有「记忆到多大之后召回精度会掉」的实测**。
L23-X 的容量水位是**读数**，不是治理。

**做什么**：
1. 三层：热（近 N 轮 + 高显著度，常驻）/ 温（可召回，按需加载）/ 冷（归档，需显式唤醒）；
2. 分片：按会话/纪元切片，单次召回只扫相关分片（与 O2 的索引共用同一份结构）；
3. 迁移规则确定性：升降温依据可复算（显著度 + 新近 + 引用次数），**同一输入必得同一分层**；
4. 实测「记忆量 vs 召回命中率」曲线，给出**精度开始下降的规模点**，写进结论（不是拍脑袋设上限）。

**验收口径**：同一记忆库在分层前后，**高层召回的命中结果集不变**（分层只影响成本不影响正确性）；
降温后的记忆仍可被显式唤醒；给出规模-精度曲线的实测点，不许只写「更省内存」。

## O5 · 写入幂等：重复记忆与冲突合并

**缺什么**：抽取是「每轮抽一次」，同一事实在十轮里会被抽十条近似记录。
仓库有冲突裁决（`conflict-adjudication-bench.js`）与修正事务（`fact-correction-transaction.js`），
但**入口没有去重**：重复记录会一路写进库，再由下游各自处理。

**做什么**：
1. 写入口幂等键：`(主体, 谓词, 客体, 时间桶)` 归一化后比对，命中即**合并而非新增**；
2. 合并策略三态：`same`（完全一致，只更新引用次数）/ `refine`（新增信息，保留两版并标出差异）/ `conflict`（冲突，转裁决台）；
3. 抽取抖动不得导致抖动写入：同一段对话重复抽取两次，**库内条数不变**（幂等）；
4. 合并留痕：每次合并写回执（合并了哪几条、依据什么）。

**验收口径**：同一对话抽取两次，库内记忆条数不变、内容逐字段一致；
十轮近似表述合成一条且保留每轮的原文出处；冲突项进入裁决台而不是被静默覆盖。

## O6 · 设置面重构：从表单堆到可理解的控制台

**缺什么**：`settings-ui.js` 5787 行，是用户唯一能看见的界面。它的问题不是长，是**「设了会怎样」不可见**：
每个开关只写名字，不写影响；改完之后没有任何反馈说明「现在召回变宽了 / 注入多了」。
本期 O1 引入了三路与预算，如果没有一个面能看见，用户只会把开关全关掉。

**做什么**：
1. 设置项登记制：`{id, group, label, default, effect, impact}`，`impact` 是**可计算的读数**（如「预计每轮多注入 2 条」）；
2. 分组按用户任务：记忆什么 / 怎么召回 / 注入多少 / 数据与隐私 / 高级；
3. 每项旁边显示**当前生效值 + 默认值 + 是否偏离**（一眼看出改过什么）；
4. 一键回到默认（分组级与全局级）。

**验收口径**：全部现有设置项一项不少（登记表条数 = 现有控件数，差异逐条列出）；
每项的 impact 读数在同一配置下可复算（不是写死的文案）；
截图对拍：默认配置下界面与 v3.474 信息量不减少。

## O7 · 诊断可读化：把三片读数变成用户能懂的一页

**缺什么**：`engine-diagnostic-lines.js` 三片共 6123 行，`engine-self-check.js` 135900 字节 ——
这些是**给开发者看的**。普通用户遇到「角色怎么又忘了」，能看到的只有控制台里的
`[LonSha记忆引擎]` 日志。仓库有 `memory-checkup.js`（3252 字节），但只做基础体检。

**做什么**：
1. 一页「记忆体检」：库存总量 / 近 7 天新增 / 召回命中率 / 注入次数 / 冲突数 / 被遗忘处置数；
2. 每个读数带**「这意味着什么」**一句话（人话，不用术语）；
3. 「为什么这条没被召回」查询：输入一条记忆，说明它没进候选的原因（显著度 / 分层 / 时效 / 被排除）；
4. 导出为文本，用户可直接贴给开发者。

**验收口径**：六项读数与引擎内部读数**同源**（同一函数，不许各算一遍）；
「为什么没召回」对三种原因各自给出不同答案；导出文本不含内部对象路径。

## O8 · 压缩与真删除：让「忘记」真的发生

**缺什么**：`memory-gc.js` / `hierarchical-compaction-ledger.js` / `tiered-storage-tiered-compaction-ledger.js`
都在做「压缩」，但压缩的产物仍然留在盘上；`forgetting-explanation.js` 只解释「为什么忘了」。
**用户要求删掉某段记忆时，没有任何路径能真的删除**（这也是 X5 隐私面的前置）。

**做什么**：
1. 三级删除语义：`mask`（不再注入、不再召回，仍留审计）/ `purge`（物理删除内容，留墓碑）/ `purge_all`（含墓碑，不可恢复）；
2. 删除必须**级联**：记忆本体 + 索引条目 + 摘要引用 + 注入回执里的快照，四处同批处理；
3. 删除后自证：召回、证据、时间线三个面都再也查不到（逐面验证）；
4. 压缩前的原文与压缩后的摘要**双留**，压缩不销毁原文（除非用户选 `purge`）。

**验收口径**：`purge` 后四处（本体/索引/摘要引用/回执）全部查不到；
`mask` 后仍可审计但零注入（注入次数实测为 0）；`purge_all` 后不可恢复（重启后仍查不到）。

## O9 · 宿主兼容矩阵

**缺什么**：本仓大量依赖 `Proxy`（`_libs` 实时视图）、`structuredClone`、`crypto.randomUUID` 等现代 API。
老宿主上会怎样，仓库只用一句「无 Proxy 的老宿主退化为快照——这条不等价，也不假装等价」带过
（PLAN v23 L23-O5 边界）。**没有兼容矩阵，没有降级清单，没有「哪些能力会缺」的用户可见说明**。

**做什么**：
1. 能力探测：启动时探测 8 项关键 API（`Proxy` / `structuredClone` / `crypto.randomUUID` / `WeakRef` / `Intl.Segmenter` 等）；
2. 兼容矩阵：每项 API 缺失时**哪些功能降级、降级成什么、有什么可感知差异**（表格化，写进文档与设置面）；
3. 降级不得静默：缺能力时读数面 `capability-missing` + 名称，用户能看见；
4. 至少在一档「无 Proxy + 无 structuredClone」的模拟环境里跑通主链路（装载/写入/召回/注入）。

**验收口径**：模拟老宿主下主链路可用（装载→写→召回→注入全通）；
每项缺失能力都有对应的可感知差异说明（不是「可能有影响」）；能力齐全时零降级分支被走到（读数证明）。

## 批次与依赖

- **A 批（正确性，先做）**：`O1` → `O5` → `O8`（召回内核、写入幂等、删除语义三者决定「数据对不对」）
- **B 批（成本，依赖 A 的结构）**：`O2` → `O3` → `O4`（索引、装载、分层共用同一份结构，顺序敏感）
- **C 批（可理解，依赖 A+B 的读数）**：`O6` → `O7` → `O9`

## 本期纪律

1. **不把门禁当内容**：每项交付自带判据，不单独成项、不占名额。
2. **确定性优先**：O1/O2/O4/O5 都要求「同一输入必得同一输出」，随机与抖动一律视为缺陷。
3. **读数不手抄**：本文数字取自仓库已落盘台账；施工时实跑，未跑过的不写进结论。
4. **降级必须可见**：任何「能力缺失 → 静默变慢/静默变差」都按缺陷处理。
