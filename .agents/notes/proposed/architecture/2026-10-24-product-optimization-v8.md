# Agent Note: 第八期 LonSha 优化提升——让记忆成为可控制、可解释、可恢复的工作介质

Status: proposed

## Problem

规划基线是 LonSha `v3.371.0`、提交 `c17c33b`。第七期已经完成记忆收件箱、事实修订、召回校正、视角预览、生成前材料计划、生成后事实回执、维护会话、人物/主题档案、项目迁移，以及口述史、传承谱系、主题策展、受证据约束访谈、关系修复、创作灵感、未完成约定、集体记忆协商和可玩档案馆。

当前真实问题不是“记忆模块数量不足”，而是系统已经拥有大量语义，却缺少一套用户可以长期依赖的操作方法：用户不知道本轮记忆采用的是哪种工作模式，冲突解决后的理由难以回看，时间变化与来源变化的影响仍需要手工追踪，召回反馈很难转化为明确可撤销的规则，迁移和批处理的风险也不够接近普通用户的理解方式。

第八期优化要把 `memory-inbox`、`fact-correction-bench`、`generation-memory-plan`、`generation-fact-receipt`、`memory-maintenance-session`、`memory-migration-boundary`、`recall-correction`、`knowledge-trace` 和现有 engine 管线组织成“记忆工作台”，但不建第二套记忆数据库，也不把审计脚本伪装成产品。

## Proposal

### M8-O1 · 记忆工作模式：让用户明确当前这轮记忆服务什么目标（P0 / XXL）

- **用户结果**：用户可以选择“剧情连续、事实核对、角色视角、研究整理、创作准备”等模式，系统据此组织召回、材料和展示重点。
- **真实落点**：组合 `memory-config.js`、`generation-memory-plan.js`、`material-pack.js`、`projection-pipeline.js`、`settings-ui.js` 与现有 prompt 生命周期；模式只改变选择和解释，不改变事实所有权。
- **完整交付**：模式预览、默认/临时模式、每轮覆盖、模式冲突提示、模式关闭后的旧行为、持久化和跨项目边界。
- **验收**：同一问题在剧情模式与核对模式返回重点不同但证据可回源；模式不能泄漏秘密或把推断变事实；重开恢复模式；插件缺席时手机侧仍能运行。

### M8-O2 · 冲突裁决台：让矛盾事实的处理有理由、有保留、有撤销（P0 / XXL）

- **用户结果**：面对互相矛盾的年龄、地点、关系或事件，用户能看到冲突来源、时间、知情范围和可选处置，而不是被一个隐式排序结果替代。
- **真实落点**：深化 `fact-correction-bench.js`、`fact-version.js`、`evidence-solver.js`、`testimony-board.js`、`relation-history.js` 和 `node-rollup.js`；裁决输出“采用/并列/待确认/撤回”，不产生不可解释分数。
- **完整交付**：冲突分组、证据对照、按视角并列、用户裁决、撤销裁决、受影响下游清单和保留原始来源。
- **验收**：同一人物三条来源的冲突可分别进入四种处置；裁决只影响相关查询；撤销后下游重新显示待定；已撤回证据不能因排序又复活；20 个依赖场景中无静默覆盖。

### M8-O3 · 时间有效性工作流：把“曾经为真、现在仍真、未来计划”彻底分开（P0 / XL）

- **用户结果**：用户能查看某条记忆在何时成立、何时被知道、何时失效，以及失效后哪些结论需要复核。
- **真实落点**：组合 `dual-time.js`、`fact-lifecycle.js`、`story-clock-parse.js`、`condition-patch.js`、`stale-guard.js` 和 `event-chain.js`；不以当前系统时间猜测故事时间。
- **完整交付**：发生时间/获知时间双轴、有效期、计划/发生/取消/未知状态、时间无法判断的具名原因、批量复核和历史视角。
- **验收**：过去事实、当前状态、未来承诺和被取消计划四类同时存在；切换故事时间不会改写历史；缺日期不补“今天”；失效事实不会继续进入当前材料；回滚可恢复前态。

### M8-O4 · 召回路线编排：让用户决定系统如何找到答案，而不是只校正结果（P1 / XXL）

- **用户结果**：用户可以选择优先经历、证据、关系、资料或角色视角，并能看到不同路线为何产生不同答案。
- **真实落点**：复用 `engine-recall.js`、`evidence-query.js`、`recall-filter.js`、`recall-correction.js`、`knowledge-trace.js` 和 `recall-explain.js`；路线是可见策略，不暴露或训练隐式黑箱权重。
- **完整交付**：路线模板、候选来源预览、排除理由、同名消歧、路线保存、单次覆盖、反馈撤销和路线效果对照。
- **验收**：同名人物/同名事件通过三条路线得到可解释差异；校正只影响指定路线或来源类型；清除校正后恢复基线；任何答案仍显示证据和未判部分。

### M8-O5 · 记忆预算编排：把有限上下文变成用户能参与的取舍（P0 / XXL）

- **用户结果**：生成前用户知道哪些材料会被带入、哪些会被挤出、哪些冲突需要先解决，并能保存自己的取舍。
- **真实落点**：深化 `generation-memory-plan.js`、`material-pack.js`、`cost-ledger.js`、`projection-pipeline.js`、`injection-receipt.js` 和现有预算 owner；不造第二套裁剪器。
- **完整交付**：必需/可选/冲突/未知分层、用户锁定材料、按角色视角差异、超预算降级、实际消费与计划对照、下一轮可复用预案。
- **验收**：三角色同场得到不同材料；用户排除私密项后实际注入不含该项；预算不足时明确牺牲项；计划与实际差异可回源；重开后锁定项仍有效但换项目不继承。

### M8-O6 · 生成结果回放：让用户看见一条新事实是如何进入长期记忆的（P0 / XXL）

- **用户结果**：一轮生成后，用户能从正文中的候选事实回到原句、影响面和确认结果，而不是面对不可逆的自动写入。
- **真实落点**：连接 `generation-fact-receipt.js`、`memory-inbox.js`、`fact-version.js`、`floor-ledger.js`、`summary-provenance.js` 和 `engine-persistence-ops.js`。
- **完整交付**：候选抽取、原句定位、事实/推断/草稿分层、逐条采纳/编辑/拒绝/延期、楼层回滚一致性、回放和撤销。
- **验收**：同一楼层混合四种内容时分别处理；拒绝项不进入摘要和下一轮注入；采纳项保留来源；楼层回滚后候选、确认和版本关系不残留；缺正文时如实显示不可回源。

### M8-O7 · 维护批处理：用可预览的批次处理长期积压，而不是把数量下降当成功（P1 / XXL）

- **用户结果**：用户能按冲突、过期、常被召回、缺来源或项目范围筛选一批记忆，预览每项动作并随时暂停或撤销。
- **真实落点**：深化 `memory-maintenance-session.js`、`memory-gc.js`、`archive-shift.js`、`memory-supersede.js`、`correction-plan.js` 和 `engine-repair-ops.js`。
- **完整交付**：批次建立、分组、逐项排除、合并/拆分/归档/延期、影响预览、凭证、断点续做、批次撤销和人工内容保护。
- **验收**：事实、承诺、研究各有一批；暂停后下次从原位置继续；错误合并可拆开并恢复引用；被用户锁定或撤回的内容不被 GC 处理；批次空结果与模块缺席不同形。

### M8-O8 · 项目边界与跨项目接续：让记忆迁移变成可审阅的关系图（P0 / XXL）

- **用户结果**：用户在复制、拆分、归档或接续项目时，能知道每条事实带走的原因、依赖、知情范围和无法带走的部分。
- **真实落点**：组合 `memory-migration-boundary.js`、`project-registry.js`、`branch-semantics.js`、`volume-continuation.js`、`secret-ledger.js` 和 `memory-package.js`。
- **完整交付**：迁移图、源/目标差异、共享事实与私密事实分列、同名对象确认、依赖闭包、匿名化、冲突处理、撤销迁移和未迁清单。
- **验收**：三个项目含同名人物、共享经历和秘密；选择迁移后目标侧逐条可回源；权限未知默认不外带；撤销只清目标增量不动源；接续包缺 owner 时明确阻断而不生成空壳。

### M8-O9 · 记忆可读工作台：把深层引擎能力组织成“现在可以做什么”的界面（P0 / XXL）

- **用户结果**：用户进入插件后先看到待确认、待修订、可回看、当前使用和边界风险，而不是模块名、审计术语和大量内部读数。
- **真实落点**：以 `settings-ui.js`、`memory-center.js`、`profile-dossier-view.js`、`perspective-preview.js`、`engine-report.js` 和现有 `css/lonsha-design.css` 为基础。
- **完整交付**：按用户任务组织入口，统一空/缺席/不可用/未验证四态，来源回跳，窄屏操作，最近位置，批次继续和不打扰的诊断入口；不删掉深层信息，只改变首层可达性。
- **验收**：用户可从一个入口完成确认、修订、查看依据和继续维护；缺模块和空盘不混淆；窄屏无横向溢出；关闭页面后工作位置保留；普通用户不需要理解 engine 名称才能完成任务。

## Delivery sequence

- **A：事实可信**：M8-O1、M8-O2、M8-O3。先解决模式、冲突和时间三类基础语义。
- **B：生成闭环**：M8-O4、M8-O5、M8-O6。再把召回和生成前后变成可审阅流程。
- **C：长期维护**：M8-O7、M8-O8。处理批量维护、项目迁移和可撤销边界。
- **D：产品收口**：M8-O9，联合 A-C 做窄屏、重开、真实长对话和宿主体验验收。

守卫、审计、版本、模块拆分和测试只为对应产品项提供最小证据；不单独占用第八期名额。

## Alternatives considered

- **继续增加新的记忆账本**：会让同一事实出现多个所有者；本期只扩展现有 owner 的用户操作面。
- **用单一置信分解决冲突**：无法表达并列视角、时间和知情边界；保留证据和用户裁决的多态结果。
- **让系统自动归档和自动迁移**：误删或越界的代价高；批量动作必须预览、凭证和撤销。
- **把深层能力全部暴露在首页**：会复现“工程面板压迫感”；O9 只把用户任务提到首层，诊断仍可深入。

## Acceptance criteria

九项都必须有真实用户入口、持久化结果、重开/撤销或明确的不可逆说明，并用事实/推断/草稿/用户确认的真实混合样本验收。纯内核、纯审计、纯测试、纯文档或单次模型演示不能结项；静态通过不能替代真实宿主和长对话边界说明。

## Risks

工作模式、召回路线和维护批次可能逐步形成隐藏的第二套控制系统。每个新对象必须可解释、可序列化、可撤销并归属于现有 owner；若一个功能需要复制正文或另建全局事实表，应退回缩小。
