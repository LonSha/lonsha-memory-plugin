# Agent Note: 记忆插件第四期优化提升九项——先修记错、查错与只预览不落地

Status: proposed

## Problem

2026-10-15 基线：`main@0f2f7fd`，v3.328.0；侦察开始时工作区干净，与 origin/main 同步。本次只交付计划，不改运行时代码、不抬版本、不把旧测试成绩当本轮实测。

旧第三期文件仍为 proposed，但代码已有承接：v3.320 承接 O2/O3/O9；v3.321～322 承接 O1/O4/O6/X1；v3.323 承接 X2/X3/X4；v3.324 承接 O5/O7/X9；v3.325 承接 O8；v3.327 承接 X5/X7；v3.328 承接 X6/X8。**十八项有代码不等于十八条用户旅程已闭合**：纯预览出口、夹具依赖、诊断中的调用都不能当成实际导入/写入/生成的证明。

本轮直接执行现有模块复现三类问题：
1. `memory-gc.js::mergeDuplicateCharacters` 输入两个不同 project 的同名 character 节点，输出只剩1个；它只按归一化名字分组，未尊重已有 project-registry 的同名异人边界。
2. `evidence-query.js::planQuestion('林安答应送什么生日礼物？')`：knownActors 为 `[林,林安]` 时选林，反过来选林安；promise 查询的 text 为空，生日礼物条件没有保留。
3. `lore-import.js::parseSource` 对超过40万字符输入返回 source.chars=400000、truncated=true，尾部内容不参与；`classify('过去他必须每天服药，后来已经停药。')` 返回 setting-rule/必须，而不是前史。

其余证据标为读码，不冒称已在真宿主重现。当前研发重心应是记忆质量与可用操作，不是再给这些缺口增加一层 selfCheck。

## Proposal

使用 M4 新编号。P0 为记忆内容正确性/闭环基础，P1 为质量与体验。M/L 为中型/跨模块规模。每项复用已有 owner，不新建通用审计平台或第二事实库。

### M4-O1 · 回收去重尊重身份、世界与事件范围（P0 / L）
- **现状证据｜实测+读码**：`memory-gc.js::mergeDuplicateCharacters` 仅用名字；`dedupeByText` 仅用 trim 后正文选较新向量，事件/分支/角色范围不参与。`entity-semantic.js`、`project-registry.js` 已有稳定身份与 universe 规则，但回收没有沿用。
- **用户收益与增量**：同名异人不被后台优化抹成一个；相同句子发生在不同事件时不互删。
- **落点与依赖**：GC 与现有实体/项目/事件身份函数；只合并可证明同一实体/同一来源的重复。旧档缺 ID 时保留或交用户确认，不能因为“没法确定”就合并。
- **验收**：跨宇宙同名、同宇宙同名异人、同实体别名、同文不同分支四组直接跑真实 GC；前两组不合，后两组按身份而非字面处理；边、出处和召回结果仍各归其主。再在宿主执行一次优化并重开回读。
- **不做**：不迁全库 UUID、不要求用户先清理全部历史、不以零孤儿边掩盖角色已被误删。

### M4-O2 · 问句保留主题、多人物与时点（P0 / L）
- **现状证据｜实测**：planQuestion 首个子串命中的名字获选，promise 条件只按人/账；已有 `resolveEntityAt/referentCandidates/readAt` 没有在此替代原始字符串名单。
- **用户收益与增量**：问生日礼物不会返回该人物所有承诺；问甲与乙、旧称、当时地点可得到有范围的结果或明确消歧。
- **落点与依赖**：evidence-query 复用实体解析/时间解析/现有 FILTERS；提取受控查询约束，保留主题词，多人关系不能退化为“任选其中一人”。未知指代先问清，不让 LLM 任意生成执行条件。
- **验收**：本轮人名顺序反例必须消除；至少覆盖20个固定问句及20个未调参的改写问句，含两个承诺主题、双人关系、否定、旧名、模糊时间；逐题核命中事件与歧义行为，不仅核返回键数。
- **依赖与不做**：无手机依赖；与 O1 共享身份规则。不新造实体表、不将“没识别出”默认为宽查全部事实并直接当答案。

### M4-O3 · 回答从行拼接变成有据的事件解释（P1 / L）
- **现状证据｜读码**：`composeAnswer` 顺序添加存在句及 title/detail，默认最多8句；多个计划可重复花掉额度，why 查询不是因果解释。已有 causal-chain、fact-version、summary-provenance 可供合成。
- **用户收益与增量**：直接回答“答应什么→后来怎样→为什么变”，关键原因/否定/金额不被前几行挤掉；无因果证据明确说不知道。
- **落点与依赖**：O2 后完善按事件聚合、跨计划去重、按问题分配答案预算和按需回源；必要时调用现有模型通道做受证据约束的表达，保留无模型的确定性答案。
- **验收**：同一事实被3个计划命中只说一次；答案末尾的转折/数额不遗漏；20组人工核对案例，所有关键结论指向实际支持它的证据，先后关系不能被说成因果；真实模型效果另验。
- **不做**：不只改 maxSentences、不把完整原文全部注入、不用回答更长当更准确。

### M4-O4 · 异步查询接到真实问答与资料页（P1 / M）
- **现状证据｜读码**：`evidence-query.js::queryAsync` 已有协作分片与取消；`index.js::askMemoryQuestion` 是同步出口，检索宿主未见 queryEvidenceAsync/queryAsync 消费。已有缓存不能替代主线程让出。
- **用户收益与增量**：大库查询不锁住面板；新问题可取消旧问题，部分结果不会伪装为全量。
- **落点与依赖**：复用 queryAsync 和 assemble，贯穿原生资料页与可供手机读取的异步出口；支持任务身份、取消、实际扫描进度。兼容旧同步 API，不在手机重新实现查询。
- **验收**：2万条/10万条合成库分别验查询、分页与取消；结果与同步基准一致，扫描上限触发时明确说明；真宿主输入响应与阻塞时间前后对照。手机 R4-O2 做自身交互验收。
- **不做**：不新增索引服务器、不先做多进程框架、不把 Node 压测等同浏览器帧率。

### M4-O5 · 长资料完整读取与可恢复解析（P0 / L）
- **现状证据｜实测**：`lore-import.js::MAX_SOURCE_CHARS=400000`，parseSource 直接 slice；当前明确报 truncated，但后续仍可能把部分 items 当完成输入。SNIPPET 也不能代替可回读原段。
- **用户收益与增量**：整本资料尾部人物与设定不丢；大文件可分段处理、暂停续读，清楚知道是否完整。
- **落点与依赖**：复用 text-chunk 与 lore-import，保持全文件段落/字节或字符范围映射、源 hash 与完整度；有硬上限就阻止“完整导入”确认，允许用户明确选择局部导入并标范围。正文只按现有宿主/已授权本地附件渠道保存。
- **验收**：超过40万字符及200万字符两组文件，首中尾放唯一事实；全读取后均可回源，暂停继续不重段漏段；尾部解析失败时状态必须是未完成，不能只展示前面成功数量。
- **不做**：不无限抬常量、不引外部数据库、不在未经选择时把整本书发给模型。

### M4-O6 · 年鉴、正史与旧事重现接入真实数据（P0 / L）
- **现状证据｜读码**：生产 `.js` 检索中 `_storyAnnualChapters/_storyAnnualSummary/_branchOutcomes/_pastDetails/_knownFacts/_loreConfirmedFacts` 只见读取；`_storyAnnualDeps/_branchCanonDeps/_fatedRecallDeps` 依赖这些槽。模块自检可用夹具不证明正常会话能产出内容。
- **用户收益与增量**：已有功能不再长期停在“待触发/依赖未给”；正常玩过的会话能生成真正章节、分支结局与往事候选。
- **落点与依赖**：将既有 project/summary/event/fact/knowledge owner 转为即时或按 revision 的派生输入；缺数据仍如实为空或不可判，不能用默认样例填槽。范围细分：本项只完成真实供数，不重报 X1/X2/X3/X7 的确认、编辑与生成产品。
- **验收**：不手工设置上述私有槽，从公开会话/提取入口建立最小剧情，再调用四类功能；源变更与切分支后读数更新，重开不依赖上轮实例残留。纯函数与诊断行全绿不足以收口。
- **不做**：不新增“供数完备性账本”，不在每个模块复制完整引擎状态；实施前复查动态赋值，若已存在则复用而非重复接线。

### M4-O7 · 长期压缩与遗忘保住不可替代证据（P1 / L）
- **现状证据｜读码**：`capByForgetValue` 主要按 importance/年龄/accessCount 排；`capSummaries` 删除 folded 记录；第三期 `stm-ltm.js` 已保留关键句/回源索引，但不能据此断言所有 GC、卷压缩都保住唯一来源。
- **用户收益与增量**：长期不提的关键约定和原话在回收后仍能准确想起；不会只有摘要结论却失去支持它的原文。
- **落点与依赖**：复用 summary-provenance、dependency-closure、既有归档与回收 owner；对未结承诺、身份转折、用户明确保留内容及唯一证据增加保留/归档策略，缓存可以删、原证据不能混删。依赖 O1。
- **验收**：人工可核的长篇样本经过多次摘要与3轮容量回收，首段埋入的约定/金额/原话仍能回源；已撤回事实不因保留策略复活；容量不足明确降级，不静默无限增库。
- **不做**：不再造长期库、不一律永久保留全部内容、不把“索引还在”当“正文还在”。

### M4-O8 · 纠错方案接上原生确认、写入与撤销（P1 / L）
- **现状证据｜读码**：`correction-plan.js` 明确 writes 恒0、只暂存；宿主 correctionPlanReextract/Config 主要转发/留读数。repair-loop/repair-settle 与 memory-center 已有 owner，缺口是选择范围到实际修正的一条可用路径，不是缺少另一套计划函数。
- **用户收益与增量**：选错记的一段，看到原文、新旧事实，逐项确认后真实生效；重开仍保留结果，并可分别撤销配置变更与事实修正。
- **落点与依赖**：memory-center + settings-ui 调现有 reextract/settle；暂存期间不改库，确认后走原 owner；实施前核已有 handler，已有正确写路不重复。O1/O2 提供身份正确性。
- **验收**：不调用私有方法，纯 UI 完成选范围→提案→选2拒1→确认→召回新事实→重启→撤销；未选范围字节不变，重复确认不增重复事实；真实模型未测时只认 fixture 提取闭环。
- **不做**：不以 returns.writes=0 证明“已修复”，不自动调参、不建立第三套修复状态机。

### M4-O9 · 无剧透回顾按事实可知性裁剪（P0 / L）
- **现状证据｜读码**：`story-annual.js::twoVersions` 主要按 allowedChars/knownChars 过滤，并清空 unfinished；同一已在场角色后来才揭露的秘密不等于可公开，无人物名的秘密也不能靠名单判断。
- **用户收益与增量**：读到第三章只见第三章已知信息，而不是“出现过这个人就能看他的全部秘密”；允许保留玩家已知的未完问题。
- **落点与依赖**：复用 perspective-card/knowledge-trace/fact-version 的逐事实、逐时点边界，覆盖标题/目录/摘要/正文引用；依赖 O6，给年鉴和 X8 场景包共用结果。
- **验收**：同角色后揭密、匿名秘密、旧名伪装、已公开未结伏笔四例；揭露前后内容准确切换，作者版仍可读，生成侧不接到作者版；“安全但整篇空白”不算完成。
- **不做**：不再造权限表，不用角色名屏蔽替代证据权限，不以泄漏扫描词数为唯一判据。

## 执行顺序

先 O1/O2/O5/O6/O9（事实与可用输入），再 O3/O4（查询体验），O7/O8 随对应 owner 并行。跨仓手机可先做出处与编辑恢复，不需要等待本仓全部完成。[拓展九项](../../proposed/feature/2026-10-15-product-expansion-v4.md)按数据依赖逐包接入。

## 历史裁定

[第三期优化](2026-10-12-product-optimization-v3.md)与[第三期拓展](../../proposed/feature/2026-10-12-product-expansion-v3.md)为部分重叠：已有候选保真、时段身份、分片查询、关键句、纠错暂存继续使用；本期不改写它们的历史交付事实。**差量**是 GC 未消费身份、问答未消费实体/主题、queryAsync 未进按钮链、纯计划未进实际确认，以及新模块未接真实生产数据。

第一期/第二期计划保留独特理由但不再作当前排序。旧文档 proposed 与代码完成度不一致，本轮加现状说明而不把十八项一律迁成 implemented；真实体验缺口仍明确保留。不借此发起全库文档整理。

## 第五期接续说明（2026-10-20）

本篇保留第四期的理由、版本与验证边界；后续排序由[第五期O九项](2026-10-20-product-optimization-v5.md)接管。两篇部分重叠而非完全替代：已有模块继续复用，第五期按具体语义/真实消费缺口补闭环，并明确区分新能力；不得将本篇历史“当前缺口”直接复活成从零任务。

## Alternatives considered

- **继续增加导出与自检行**：容易维持既有判据风格，但已有“出口齐全、正常会话不供数”反例，不能作为产品成果。
- **把所有缺口归为实机未验**：可避免新改动，却会掩盖直接可复现的名字误合并和问句丢条件；优先修这些实质缺陷。
- **引入新向量库/新记忆框架**：对大规模有潜力，但不能解决目前身份/主题/写入 owner 问题；先复用零依赖模块与现有存储。

## Acceptance criteria

九项各自达到用户结果，不按测试/守卫/台账条数计功。每项分别记代码/自动化、真宿主旅程、真实模型质量三种状态；本轮没有把任何一项新功能标完成。算法类对照使用固定样本加未调参样本，不能只证明返回字段齐全。

本轮文档检查只针对数量、链接、基线、已有计划裁定与现行排序；不改在役测试计数、门禁或版本真源。实施期定向验证，功能计划收口再按既有纪律跑全量 `npm test`；不因本次计划推送假报新全量成绩。

## Risks

同名合并与回收修复可能涉及旧数据，实际迁移必须备份并经确认，不可猜测恢复已被删的来源。动态依赖可能由外部消费者注入，故“生产检索只见读取”须在实际宿主复核。模型的语义理解和回顾文风不能由关键词函数或自动化通过代替。
