## M-X1 · 用户侧记忆控制中心（P1，规模 L）
**需求**：X1 已交付结构化查询能力，但仍主要是内核出口。用户需要一个能浏览、筛选、确认、处置记忆的统一界面。

**功能**：
1. 按角色、时间、楼层、来源、状态、秘密级别组合筛选。
2. 展示证据原文、来源 ref、修订链、派生关系。
3. 直接进入修复预览 / 撤回 / 标记争议 / 导出。
4. 查询条件可保存（保存的是**条件**，不是第二份证据库）。

**验收**：
- 超过 200 条的历史记录仍能分页检索（不因投影截断而漏）。
- 空 / 未知 / 缺模块 / 读取失败四态明确分开。
- 查询零写副作用。
- UI 显示来自真实查询结果，不自行猜测。

---

## M-X2 · 修复从「流程完成」到「所有派生面落盘完成」（P1，规模 L）
**需求**：X2 已交付证据到修复的完整链路。真正未收口的是：登记修复、修改原账、刷新派生数据、回读确认之间仍可能出现「流程走完但派生面没跟上」。

**功能**：
1. 选择证据 → 预览影响范围 → 用户确认方案 → 原 owner 执行 → 更新摘要 / 关系 / 时间线 / 召回缓存 → 保存并回读 → settle。
2. 失败项**单独重试**，不整批重放。
3. 所有派生内容记录 `sourceRefs / derivedFrom`。
4. 撤销只在原 owner 能提供逆操作或检查点时才开放。

**验收**：
- 仅登记不得显示「事实已纠正」。
- 部分成功显示 `partial`，不伪装全成功。
- 重试幂等；切聊后旧预览被拒绝。
- 所有派生面来自同一 revision。
- 源、摘要、图谱、时间线、召回缓存跟随同代变化。

## M-X3 · 项目 / 卷 / 章节管理面（P2，规模 L）
**需求**：X7 已具备分卷与接续机制，但缺用户层面的项目管理，接续包容易变成另一套难以管理的隐式状态。

**功能**：
1. 创建项目；管理卷与章节；绑定会话、分支、角色。
2. 生成卷末接续包（携带源会话 / 分支 / 版本 / 许可范围 / 证据 ref）。
3. 新会话先预览冲突与缺面，再选择性导入。
4. 支持项目归档与解除绑定。

**验收**：
- 未选择项目时维持**完全隔离**。
- 同名角色、不同宇宙不合并。
- 重复导入幂等；撤销有明确来源边界。
- 旧源删除后引用状态清楚，不伪装仍可跳转。

## M-X4 · 事实生命周期与「遗忘 / 撤回 / 保留」控制（P1，规模 L）
**需求**：系统擅长保存与召回，但用户还需要明确控制哪些内容继续存在、哪些应被撤回或降级。

**功能**：
1. 对事实设置：保留 / 过期 / 撤回 / 仅作者可见 / 禁止角色使用。
2. 区分四种动作：删除原文、撤回派生、隐藏于生成、保留审计记录。
3. 支持按来源、角色、项目、时间范围批量处理。
4. 所有操作生成可回滚记录。

**验收**：
- 选择「禁止生成」不得误删原始证据。
- 撤回后不进入召回与模型载荷。
- 保留审计时不得泄露受限正文。
- 操作可回读、可撤销、可审计。

## M-X5 · 角色知识传播的可见范围预演（P2，规模 M–L）
**需求**：X5 已记录角色如何获得知识。下一步让用户在写剧情**之前**预演「如果公开 / 转述 / 私聊，会影响谁」。

**功能**：
1. 选择一条事件或秘密。
2. 预览五条传播路径：公开、转述、私聊、误信、纠正。
3. 展示各角色的可知 / 不可知 / 未知状态变化。
4. 只生成提案，不直接改变事实或角色知识。

**验收**：
- 预演零写账、零改角色知识。
- 同一传播事件不生成多条重复证据。
- 回档后未来传播状态可撤销。
- 作者预览面与角色生成面**严格分离**。

## M-X6 · 手机事实桥 2.0：确认、撤回与双向回执（P1，规模 L）
**需求**：X4 已完成手机事实受控准入，但长期使用还需要处理手机侧的编辑、删除、撤回与记忆侧回执。

**功能**：
1. 手机侧产生事件 → 记忆插件判断准入 → 用户确认或拒绝 → 记忆侧写入 → 返回 `accepted / rejected / pending / revoked` → 手机侧显示最终状态。
2. 覆盖三类事件：财务事件、日历约定、明确完成的剧情事件。
3. 同源跨平台转发保留 `rootEventId`，去重只进一次。
4. 手机侧编辑 / 删除后，记忆侧能换代或撤回。

**验收**：
- 预测、报价、草稿不自动变成事实。
- 同一 `rootEventId` 只入账一次。
- 任一插件单独安装都有可解释降级。
- 新面两仓各自登记与对账；反向面不塞进正向登记表。

## M-X7 · 提取质量反馈与可控策略配置（P2，规模 M–L）
**需求**：模型选择、提取与规则机制已具备，召回解释（X8）也已交付。缺的是**用户反馈入口**：这次为什么提取错、怎样减少同类错误。

**功能**：
1. 用户标记五类问题：漏记 / 错记 / 错角色 / 旧事实未被替换 / 不应记录。
2. 反馈关联原文与提取版本，保留原始依据。
3. 生成策略建议，但**默认不自动修改任何事实或配置**。
4. 用户确认后才调整提取或召回配置；建议须以同候选重跑对照为依据（复用 X3 的对照机制）。

**验收**：
- 反馈不得直接成为历史事实。
- 建议来自真实 trace 与对照重跑，不由模型编原因。
- 自动调参默认关闭；坏源失败时解释可降级。
- 调整后必须在留出集上证明改善，而不是只优化当前样本。

## M-X8 · 版本化记忆包与跨设备迁移（P1，规模 L）
**需求**：长期使用后，用户需要把项目、角色、事实与知识边界安全带走，而不是只能依赖当前宿主存档。

**功能**：
1. 导出粒度：项目级 / 角色级 / 会话级。
2. 包内容：schema 版本、`sourceRefs`、revision、知识范围、迁移说明、敏感字段标记。
3. 导入流程：预览 → 冲突检测 → 部分导入 → 撤销。
4. 优先本地文件，不默认联网，不新增外部数据库或云同步。

**验收**：
- 旧版本包明确迁移或明确拒绝（不得静默丢字段）。
- 同一包重复导入幂等。
- 过期 `sourceRef` 显示悬空，不伪装可跳转。
- 秘密与受限知识不因导出而放宽权限。
- 会话与分支边界不能被导入打穿。

## M-X9 · 统一记忆工具 API 与手机可消费投影（P1，规模 L）
**需求**：RubyPhone 已有查询、续玩、事实准入、来源链等需求。如果每次都依赖本仓内部模块名，跨仓联动会持续产生脆弱接线（历史教训：下游门禁 R3 是双向对账，按名配对看不见「同体不同名」）。

**功能**：
1. 定义稳定的**只读** API 面：
   - `queryEvidence`
   - `getContinuityPack`
   - `previewFactAdmission`
   - `explainRecall`
   - `getKnowledgeBoundary`
2. 统一返回状态：`ok / empty / unknown / unavailable / partial`（五态不同形）。
3. 每个返回值携带来源、revision、范围与能力版本。
4. 写操作仍由本仓内部 owner 控制，API 面**不开写口**。
5. 注册进 `open_face_registry.tsv`，并按既有纪律做双向对账。

**验收**：
- 下游不依赖本仓内部文件路径。
- 缺某一接口时能降级，**不静默返回空数据**（空与缺席不同形）。
- 投影不复制第二份事实库。
- 同一份输出可用于诊断、手机 UI 与测试夹具三种场景。
- 与 ruby-phone R-X4 / R-X8 成对核对契约。
