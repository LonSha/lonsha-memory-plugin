# Agent Note: LonSha 记忆引擎拓展计划（深度、广度与新功能）

Status: proposed

## Problem

引擎的核心机制已经很厚：九账、事实版本、事件完整性、修复闭环、投影、成本预演和检查点都已在代码中。新增价值应来自用户能查询、纠错、调参和管理长篇剧情，而非再给既有机制换一个名字。

本轮基线为 v3.271.0 / `1a0ba36`。证据面已支持 `search(face,query,opts)`、账别筛选与 `findRef`，每账投影至多 200 条、正文至多 160 字；查询的是投影面，不能直接宣称搜索了全部历史。修复桥已有 preview/apply/settle/abandon 与修订/幂等门，但登记修复与真正修改派生内容是不同动作。以下 X1–X8 均为未实施提案。

## Proposal

### X1 · 结构化证据查询与完整度（深度深化，P1，规模 M–L）

现状：九账关键词检索和 ref 已有，actor 等字段部分被折成 detail 文本；缺按角色、楼层区间、剧情时间、状态、来源与修订的统一结构化查询。

内容：为原账投影保留结构化参与者、来源身份、有效时间与可用性；提供组合筛选、分页、排序、保存查询。分页应由原账只读取数，不默认在 200 条摘要中找不到就判全库没有。结果报告扫描范围、截断、空账、缺模块、未知楼层；稳定 ref 由 owner 的主键产生，缺键时可读但不声称长期可定位。

验收：超过 200 条的旧证据仍能按需检索；同名异人、楼层 0/未知、编辑正文、旧修订、空/缺席均分开；筛选无写副作用；查询重放一致，保存的是查询条件而非第二份证据库。RubyPhone 全局搜索与织光机可消费同一结果。

### X2 · 证据到真实修复的操作流程（新产品流程，P1，规模 L）

现状：repair-loop 已有三类动作、六类受影响项与终态，但 affectedBy 用文本 mentions-needle 判候选，正文只看前 200 字；bridge.apply 是登记，不会自动改摘要/关系/事实。这不是“修复功能从零开始”，而是使已有机制可操作且可证明修完。

内容：用户选错项→看原文和候选影响→选择纠正归属/拆分/撤销→逐项确认修改方案→原 owner 执行→保存并回读→settle。新派生内容逐步记录 sourceRefs/derivedFrom；按确切依赖引用找影响，旧内容的文本命中只标候选，并报告未覆盖范围。保留 preview、幂等键、会话/修订门，失败项单独重试，撤销操作在原 owner 能提供逆操作/检查点时才开放。

验收：仅登记不能显示“事实已纠正”；只有原数据与持久化回读均证明修改才记 done；部分失败保留 partial；源、摘要、图谱、时间线与召回缓存跟随同代变化；切聊后旧预览拒绝，重复点击不重复改。依赖优化 O1/O2/O4。

### X3 · 注入策略对照与精确预演（深度深化＋新调参流程，P1，规模 L）

现状：cost-forecast 已复用真裁剪；projection 的世界书容量预演 v3.270.0 已交付。它目前算 enabled && constant 的常驻占用，`atRisk.basis='tail-first'` 只是尾部样本；不能称为完整实际激活预演或准确“被挤掉清单”。

内容：冻结同一次候选与会话身份，比较多个预算、策略和来源开关；只调用真裁剪并消费 trace，精确显示留下/挤掉/半截的 ref、最终载荷、成本、常驻溢出与不同方案差异。由 RubyPhone worldbook-dryrun 或已核对的宿主出口提供真正激活条目，区分 exact/constant-only/unknown，避免世界书占用已包含于 reserve 时重复扣。可保存方案，应用是显式配置动作。

验收：给同一输入的预演与实际路径一致；对照不调用模型、不写账、不改当前开关；未取得实际激活时只报告有限范围；禁用条目不计实际注入，非激活内容不计；保留 projection API v1 消费兼容或做双仓明确迁移。依赖优化 O3/O4，与 RubyPhone X8 配套。

### X4 · 手机事实受控准入（广度拓展，P1，规模 L）

现状：反向桥已登记 1 面并消费 backfill/recall/floor 生命周期；这并不代表手机所有 App 事实已成为可靠引擎事实。usage-tracker 是玩家使用行为，不应默认转成角色剧情记忆；traveldesk 是分摊费用，不是旅行行程。

内容：先接两条高价值候选：明确完成的日历/约定事件、用户确认入账的财务事件；后续可选健康状态的既定记录。使用 chatId/branchId/eventId/revision/sourceFloor/storyTime/status/visibility 的准入契约，区分 observed/confirmed/predicted/draft/quoted。同源跨平台转发保留 rootEventId，去重只进一次；编辑、撤回、删楼能通知 owner 撤销/换代。复用现有 native-tools、状态机与账本，不旁路写 graph 私有字段。

验收：同事件重试不增条，未来预测/报价不成已发生事实，错会话/旧代拒绝，原始记录可追溯；关闭来源真正不注入；手机单装、插件单装、旧版缺能力都可工作并有原因。新面两仓各自登记与对账，反向面不塞正向登记表。依赖两仓保存与边界优化。

### X5 · 角色知识演变与传播证据（深度深化，P1/P2，规模 L）

现状：secret-ledger、knowledgeOwners、relation-disclosure 和下游 knowledge-contract 已有谁知道什么的约束；新增的是知识取得/撤回/误信的时间轨迹及跨平台传播。

内容：按角色查看“在第几楼/剧情时刻，从谁、哪条原始证据得知/怀疑/误信/被纠正”。将保密、谣言、转述、伪装身份与同名异人保留为不同状态；生成查询、全局检索、手机通知共同按角色知情范围过滤。玩家可查的作者面与角色可用的生成面分开，避免作者证据直接喂角色。

验收：角色在获知之前不引用秘密；同文转述不变成两条独立证据；回档撤销之后的知识；身份揭穿前按明面身份，揭穿后可查变化来源；未知不等于知道或不知道。依赖 X1/X4，联动 RubyPhone X5；现有知识约束不重复重建。

### X6 · 分支语义对照与受控交接（深度深化＋新流程，P2，规模 L）

现状：branch-guard、快照恢复预检、检查点键/内容差异已交付，不能把“从零做分支 diff”列待办。当前还可深化用户能理解的角色/事件/约定变化与依赖影响。

内容：两分支只读比较时，按 owner 的实体 id 显示事实版本、角色状态、未了事项、金钱和剧情时间变化；关联来源楼层与不同有效范围。从历史分支带回条目是逐项提案，先识别目标冲突、知识边界与派生依赖；提供导入草稿、预检、确认与回执，避免全档自动合并。

验收：对照不改当前分支；未知字段与缺模块明确列出；A 分支秘密不混入 B；冲突不能由“较新”一律覆盖；导入重试幂等、可回源、保存后回读；需要恢复时走既有 owner 与 epoch。依赖 O1、X1/X2，与 RubyPhone X8 联动。

### X7 · 长篇剧情分卷与选择性接续（广度拓展，P2，规模 L）

现状：卷摘要、档案、休眠、增量书签与跨会话隔离已有；“跨会话评测通过”不等于自动共享所有记忆，也不该改变默认隔离。

内容：建立用户选择的长篇项目归属与卷/章节导航，提供上一卷结束时的角色、事实、未了约定和时间锚点接续包。包带源会话/分支/版本、许可范围与证据 ref；新会话先预览冲突和缺面，再导入选中事实，禁止隐式串联同名角色。仍复用宿主持久化或现有存档路径，暂不增加外部数据库/云同步。

验收：不选项目时维持完全隔离；同名不同宇宙不合并；接续重试不重复，撤销有来源范围；秘密带知识范围；旧源删除后引用状态清楚，不能伪装仍可跳转。依赖 X1/X5/X6，与手机续玩协作。

### X8 · 召回问题解释与有证据的策略建议（新诊断流程，P2，规模 M–L）

现状：recallAudit、stages、来源开关、RRF/重排和成本账本已有；新价值是用户能问“这件事为什么没被用”并得到对应原因和可验证的改法。

内容：沿一次真实轮次 trace 展示缺源→无命中→别名/身份过滤→有效性过滤→预算裁掉→已注入各阶段；给出可执行的建议，比如核对角色别名、修复过时事实、提高特定来源预算。建议以 X3 同候选重跑比较为依据，用户选择后才改配置。可记录用户反馈，但反馈不能自动改成历史事实；保持原生工具调用与现有 API 通道复用。

验收：解释来自同一轮真实 trace、带 ref 与截断范围，不由模型编原因；建议在留出评测与实际注入对照中收益可见且不增加泄密；自动调参默认关闭，坏源失败时解释也可降级。依赖 O4/O6、X1/X3。

## Alternatives considered

全面增加向量模型、云数据库或独立协作服务的强项是扩大容量，但会引入网络、同步和新的状态 owner，当前问题主要在已有链路的正确性与可操作性，暂后置。把九账摘要全部复制到 UI 库方便筛选，却使 200 条截断与修订漂移变成第二份真源，采用原账分页查询。修复自动全局文本替换成本低，但同名、转述和弱依赖会误伤，采用 sourceRefs＋owner 执行，文本命中只作候选。分支自动合并能省操作，却可能统一平行身份与知识边界，采用逐项提案。

## Acceptance criteria

建议三批大更新：第一批 X1/X2/X3（查证、纠错、调预算）；第二批 X4/X5（手机事实准入与角色知情）；第三批 X6/X7/X8（分支、长篇接续与策略解释）。每批至少完成一个真实用户操作闭环，不以导出面或诊断行增加判交付。

所有涉及生成质量的条目同时验证正向有效与反向禁入；所有写流程同时验证预览不写、确认只写 owner、重试幂等、旧会话拒绝、落盘后回读。关联[优化提升计划](../architecture/2026-10-04-optimization-plan.md)。

## Risks

旧数据缺少派生引用，不能把补关系猜测冒充精确来源。真实宿主世界书激活面与最终请求体可能仍不可观测，必须保留范围。长篇项目与跨分支接续会扩大混淆风险，需要显式身份与选择性导入。模型建议无法证明改对，所有自动策略必须先有独立评测与可恢复配置。
