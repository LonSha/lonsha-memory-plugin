# 第二十四期 · LonSha 记忆插件拓展九项（L24-X1~X9）

> **主题：把「记忆」从后台数据变成角色与用户都能看见、能改、能证明的东西。**
> L23-X 的九座（因果链回放 / 偏差面 / 承诺兑现 / 遗忘解释 / 冲突裁决 / 排序解释 / 修订历史 /
> 容量水位 / 跨会话延续）都是**纯函数 + 一个 `/lonsha-get trace` 出口**。
> 这一层已经饱和：再加第十个 trace 资源不产生新体验。本期九项全部要求**有交互面或有跨面联动**，
> 且每项必须回答一个用户真的会问的问题。

## X1 · 记忆交互台：时间线 / 图谱 / 检索三视图

**缺什么**：本仓的记忆**只以注入文本的形式被感知**。用户想「看看它记住了什么」，
唯一入口是设置页里的统计数字。`memory-map.js`（3196 字节）、`knowledge-network.js`（15911 字节）、
`graph_algorithms.js`（15586 字节）都是**图算法内核**，没有任何视图消费它们。

**做什么**：
1. 时间线视图：按剧情时间排记忆，支持按人物/地点/事件类型筛选，点击进入单条详情（原文出处 + 关联）；
2. 图谱视图：人物-事件-地点三色节点，边权=共现强度，支持聚焦某个人物看它的关系网；
3. 检索视图：输入查询，显示三路候选与各自贡献（与 O1 同源），点开看命中片段；
4. 三视图共享同一份投影函数（**一处计算，三处渲染**），不许各算一遍。

**验收口径**：三视图对同一记忆库的条数/关系数一致（同源）；点击任一节点能回溯到原文楼层；
1w 条记忆下图谱首屏可交互（有实测耗时）；空库三视图各自说明「还没有记忆」而不是空白页。

## X2 · 记忆质量基准台：给「记得准」一个可复现的答案

**缺什么**：551 套判据全部是**结构判据**（有没有这个字段、三态是否不同形、有没有被消费）。
没有一套回答「给定这段对话和这个问题，该被召回的记忆有没有被召回」。
于是所有调参（显著度权重、衰减曲线、融合权重）都是**凭手感**，改坏了也看不出来。

**做什么**：
1. 金标集：≥30 组「对话片段 + 查询 + 期望命中的记忆 id」，覆盖同义改述、时间指代、人物指代、否定、跨会话；
2. 指标：Recall@k / MRR / 误召回率，逐组报；**每组标注为什么这条该被召回**（可人工复核）；
3. 基准台：一键跑完输出对比表（当前配置 vs 改动后），差异逐条列出（哪组变好、哪组变坏）；
4. 基准集本身是**数据不是代码**，可增删条目且不改变引擎。

**验收口径**：同一配置两次运行结果完全一致；人为把某路关掉后指标可解释地下降（证明基准有牙）；
新增一组金标只需改数据文件（不改代码）；指标计算与被测引擎**读同一份召回结果**（不另写一套判定）。

## X3 · 多模态记忆：让图片与语音进记忆

**缺什么**：本仓记忆载体是纯文本。SillyTavern 场景里角色会发图片、会有语音消息，
但这些内容**从不进入记忆**：下一轮角色完全不记得「我昨天给你发过那张照片」。

**做什么**：
1. 图片记忆：登记 `{来源楼层, 描述文本, 拍摄时间(剧情), 涉及人物}`，**描述由宿主生成侧提供**（本仓不调模型），缺失则 `undescribed`；
2. 语音记忆：转写文本（宿主提供）挂到事件上，保留「是语音」这一属性（不是纯文本）；
3. 召回：多模态条目走同一套三路检索（描述文本参与 BM25），命中后注入时**明确标注模态**（「（图片）」）；
4. 引用完整性：图片/语音被删除时，记忆条目转 `dangling` 而不是静默消失。

**验收口径**：图片记忆在下一轮对话中被召回的样例可复现；未描述图片进 `undescribed` 且不参与文本检索；
删除源图片后记忆变 `dangling` 且界面可见；注入文本里的模态标注与条目属性一致。

## X4 · 纠错闭环：用户改一条记忆，后续召回真的变

**缺什么**：仓库有 `recall-correction.js`（10084 字节）、`fact-correction-transaction.js`（21007 字节）、
`memory-revision-history.js` —— **机制齐备，但没有用户入口**。
用户看到「角色记错了」，唯一能做的是重置整个会话的記憶。

**做什么**：
1. 单条编辑：改内容 / 改归属人物 / 改时间 / 作废（`void`）四类动作；
2. 编辑即生效：下一轮召回用新内容（不是「下次重建索引后」），并标明这条被用户改过；
3. 可回滚：每次编辑进修订历史（已有），用户可一键回到任一版；
4. 影响可见：编辑后给出「这条此前被召回 N 次，最近一次在第 M 轮」——让用户知道改了会影响什么。

**验收口径**：编辑后下一轮召回命中新内容（实测一次真实召回）；作废后不再注入但审计可查；
回滚到旧版后内容与当时逐字段一致；影响面读数与历史回执对得上。

## X5 · 遗忘权与隐私面：用户能证明「它真的忘了」

**缺什么**：O8 给了删除**机制**，但用户需要的是一整套**权利面**：知道存了什么、能导出、能删、
能证明删干净了。当前没有任何一个用户可执行的路径（只有开发者能进控制台）。

**做什么**：
1. 「我的记忆」清单：按人物/时间列出全部条目，可搜索、可分页；
2. 导出：整库导出为人类可读 JSON（含原文出处），可只导出某个人物或某个时间段；
3. 删除：单条 / 某人物 / 某时间段 / 全部，四档，每档明确写「会删掉什么、保留什么」；
4. 删除证明：给一份**删除回执**（删了多少条、涉及哪些面、校验摘要），用户可留着；
5. 脱敏导出：把人物名替换为占位符后再导出（用于反馈问题）。

**验收口径**：导出→删除→再导出，两次内容差异与删除清单逐条对应；
删除回执里的条数与实际删除数一致；脱敏导出后原文名字不可见（可扫）。

## X6 · 世界共享记忆：多个角色记得同一件事

**缺什么**：`multi-char-memory-isolation`（3452 字节）解决的是**隔离**（各角色不串记忆），
`institutional-memory.js` / `collective-memory-deliberation.js` 是机构与集体层，**不是「共享事实」**。
现状：A 角色和 B 角色都经历了同一场雨，两条记忆各记一份，永远对不上。

**做什么**：
1. 事件共享层：同一事件可由多个角色各自持有「视角记忆」，**共享事件本体**（时间、地点、参与人）；
2. 共识与分歧分开：`agreed`（都说同一件事）/ `divergent`（细节不同）/ `single_witness`（只有一人）；
3. 分歧不合并：允许两条视角并存并标出差异点（谁说的不一样），**不许仲裁成一个版本**；
4. 召回时按当前在场角色取视角：A 在场时给 A 的版本，若 A 不在场但有共享事件，按 `heard_about` 标注来源。

**验收口径**：同一事件两人各记一条，事件本体只有一份（条数可验证）；
分歧事件两条并存且差异逐字段列出；A 视角召回不会返回 B 的私密细节（越界即红）。

## X7 · 多视角记忆：同一件事，不同的人记得不一样

**缺什么**：现实里记忆是有视角的（谁在场、谁只听说、谁误解了）。本仓记忆是**单一客观口径**：
一条事件一条记录，视角信息在抽取时就被抹平了。这直接导致角色「全知」——
它知道自己不可能知道的事。

**做什么**：
1. 每条事件记忆带 `witness`（亲历 / 听说 / 推断）与 `holder`（谁记得这条）；
2. 注入时按 holder 过滤：角色只能召回自己 holder 的记忆 + 公开事件；
3. 「听说」必须带来源（谁说的），来源不可考则 `hearsay_unknown`（不许当成亲历）；
4. 与 X6 共享层联动：公开事件所有人可见，私密视角只 holder 可见。

**验收口径**：构造「A 亲历、B 听说、C 不在场」三场景，C 召回不得包含该事件；
B 的注入文本带「（听 A 说）」标注；holder 过滤不生效时判红（负控制）。

## X8 · 记忆时间机器：回到某一轮，看差异

**缺什么**：`snapshot-checkpoint.js`（37769 字节）有快照，`ledger-replay.js`（61561 字节）有回放，
但**用户视角没有「回到上周三的记忆状态」**这个动作，也没有「两个时点的记忆差异」。
出问题时无法定位「是哪一轮开始记错的」。

**做什么**：
1. 时点快照：按轮次/时间点打标记（自动 + 手动），保留该时点的记忆库摘要；
2. 差异对比：任选两个时点，输出「新增 / 修改 / 删除 / 状态变化」四类差异，逐条可展开；
3. 回滚：回到某时点（**生成新分支而不是覆盖历史**，历史不可变）；
4. 定位辅助：「这条记忆第一次出现是在第 N 轮」，点进去看当时的原文。

**验收口径**：两时点差异条数与实际变更一致（用编辑历史交叉验证）；
回滚后库内容等于该时点快照（逐字段对拍）；回滚不破坏历史（旧时点仍可访问）。

## X9 · 注入面透明化：这一轮到底注入了什么

**缺什么**：`injection-receipt.js`（26012 字节）与 `injection-router.js`（23934 字节）记录了注入，
但**用户看不到**。用户能感知的只有「角色好像知道 / 好像不知道」。
当注入把不该说的内容塞进上下文（剧透、已作废记忆、别人视角的私密），没有任何面能发现。

**做什么**：
1. 「本轮注入」面板：列出这一轮注入的每一条记忆（内容摘要 + 来源 + 为什么被选中 + 占多少字符）；
2. 可临时禁：某条本轮不注入（只影响本轮，不改库），并记录用户手动排除；
3. 预算可见：注入总字符数 / 预算上限 / 因预算被裁掉的条目（**裁掉要报，不许静默丢**）；
4. 剧透防护：标记为「未来事件」的记忆默认不注入（可显式开启），命中即读数可见。

**验收口径**：面板列出的条目与实际注入文本逐条对应（不多不少）；
临时禁用的条目本轮确实没进上下文（实测）；被裁掉的条目数与预算计算一致；
未来事件记忆默认零注入（负控制：强制开启后可注入）。

## 批次与依赖

- **A 批（先有面，才有用）**：`X1` → `X9`（先能看见库，再能看见注入）
- **B 批（先有度量，才敢改）**：`X2`（基准台是 O1/O4 调参的前提，建议最先做）
- **C 批（数据模型扩展）**：`X3` → `X6` → `X7`（多模态、共享事件、视角三者共用事件模型）
- **D 批（用户权利）**：`X4` → `X5` → `X8`（纠错、隐私、时间机器都依赖 O8 的删除语义）

## 本期纪律

1. **每项必须回答一个用户真的会问的问题**，答不上来的项直接砍（本仓不缺第十个 trace 资源）。
2. **一处计算，多处渲染**：视图与判定不得各算一遍（X1/X9 都会被这条审）。
3. **不猜测、不仲裁**：分歧与不确定各自成态（X6/X7），禁止仲裁成一个「标准版本」。
4. **越界即红**：视角/隔离类（X6/X7）必须有负控制证明「不该看见的看不见」。
